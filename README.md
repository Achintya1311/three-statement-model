# Three-statement model from primary filings

Educational research on historical data. Not investment advice. Not a SEBI-registered research analyst.

**Question:** of the ten growth/margin/rate assumptions a three-statement forecast depends on, which ones actually move the FY-final net debt/EBITDA result, rather than being assumed to matter?
**Method:** shock each of the ten override levers up and down from its own real historical default, one at a time, and rank by the resulting swing in FY-final net debt/EBITDA (not revenue CAGR or EBIT margin, which a growth/margin override determines almost tautologically).
**Finding (Day 7):** dividend payout ranks #1 (0.34x impact) and domestic revenue growth #2 (0.21x) — ahead of capex margin, NWC margin, tax rate and the rest (down to 0.01x) — though dividend payout's ranking is partly an artifact of its own zero floor, named as such rather than hidden.
**Chart:** none — this repo's output is a live-formula Excel workbook, not a chart; see `outputs/GULFOILLUB_model.xlsx`.
**Reproduce:** `python -m model.sensitivity --ticker GULFOILLUB`

A fully linked income statement, balance sheet and cash flow forecast built from the filings with no template underneath, where the balance check is a test that fails loudly.

**Status:** Complete (Oct 2026). Part of a nine-repo equity research pipeline; [STOCKSTALKER](https://github.com/Achintya1311/STOCKSTALKER) is the front door.

## What this is

Revenue is built from operating drivers rather than a growth percentage. Debt carries a real schedule with mandatory amortisation, a revolver and interest on average debt behind an explicit circularity toggle.

Exports to Excel with live formulas and assumptions in one marked block, because a workbook of pasted values cannot be interrogated.

## Correctness gate

pytest asserts assets = liabilities + equity across every forecast year with no unexplainable plug, and the workbook opens with live formulas.

This is the test that decides whether the repo is finished. A result that has not passed it is a draft.

## How to run

```bash
uv venv && source .venv/bin/activate
uv pip install -r requirements.txt

# Day 1: ingest a ticker's historical financials into the normalized schema
# (model/historical.py) and report per-year margins, net debt and the
# realized revenue CAGR. Offline by default - reads the committed
# data/<ticker>/financials.csv.
python -m model.ingest --ticker GULFOILLUB

# Day 2: driver-based revenue build (model/revenue_driver.py) - domestic vs.
# export revenue reconciled against the Day 1 fixture, each segment's own
# historical CAGR, and a forward forecast using each segment's own growth
# rate (overridable per segment).
python -m model.revenue --ticker GULFOILLUB
python -m model.revenue --ticker GULFOILLUB --forecast-years 3 --domestic-growth 0.10 --export-growth 0.15

# Day 3: cost structure, D&A, capex and working-capital schedules
# (model/schedules.py) - each expressed as a margin of revenue, defaulting to
# a trailing historical average (overridable), chained onto Day 2's revenue
# forecast rather than re-deriving one.
python -m model.costs --ticker GULFOILLUB
python -m model.costs --ticker GULFOILLUB --forecast-years 3 --ebitda-margin 0.15 --capex-margin 0.02

# Day 4: debt schedule (model/debt_schedule.py) - mandatory amortization,
# revolver draw/cash-sweep, and interest on the average debt balance behind
# an explicit circularity toggle. Chains onto Day 3's EBITDA/capex/working-
# capital forecast for a pre-tax, pre-interest cash-available-for-debt-
# service (CFADS) proxy.
python -m model.debt --ticker GULFOILLUB
python -m model.debt --ticker GULFOILLUB --forecast-years 3 --no-circular
python -m model.debt --ticker GULFOILLUB --amort-rate 0.05 --revolver-limit 40000 --interest-rate 0.07

# Day 5: full three-statement linkage (model/linkage.py) - chains Day 2/3/4's
# forecasts into a full income statement, cash flow and balance sheet, and
# checks assets = liabilities + equity for every forecast year.
python -m model.statements --ticker GULFOILLUB
python -m model.statements --ticker GULFOILLUB --forecast-years 3 --no-circular
python -m model.statements --ticker GULFOILLUB --tax-rate 0.25 --dividend-payout 0.2

# v0.8: write the fundamentals contract Stock Stalker reads (requires
# --forecast-years >= 3 and a passing balance check) -- see "Where this sits"
python -m model.statements --ticker GULFOILLUB --contract outputs/fundamentals_contract.json

# Day 6: Excel export (model/excel_export.py, model/build.py) - writes an
# .xlsx workbook with an Assumptions sheet (every rate/margin/limit, the
# only place a number is typed in) and a Forecast sheet that is formulas
# past the Base column, chaining off Assumptions and the previous column -
# never a Python float baked into a formula string. Non-circular mode only
# (see model/excel_export.py's module docstring for why that removes both
# of Day 5's circularities at once, not just Day 4's).
python -m model.build --ticker GULFOILLUB --years 3 --export outputs/GULFOILLUB_model.xlsx
python -m model.build --ticker GULFOILLUB --years 5 --tax-rate 0.25 --dividend-payout 0.2

# Day 7: sensitivity (model/sensitivity.py) - shocks each of the ten
# growth/margin/rate assumptions individually (Day 2/3/4/5's own override
# flags), ranks them by how far FY-final net debt/EBITDA moves, and grids
# the top two against each other.
python -m model.sensitivity --ticker GULFOILLUB
python -m model.sensitivity --ticker GULFOILLUB --no-circular --steps 1

# Day 8: the worked "what happens if they draw the revolver in year two"
# scenario (model/revolver_scenario.py, CLI model/revolver.py) - every
# forecast year runs at the same real historical defaults model.statements
# uses, except the shocked year(s), which get a deliberately collapsed
# EBITDA margin. Default: a one-year shock in year 2 only.
python -m model.revolver --ticker GULFOILLUB
python -m model.revolver --ticker GULFOILLUB --shock-year 2 --shock-ebitda-margin 0.05
python -m model.revolver --ticker GULFOILLUB --shock-year 2 --shock-duration 3 --forecast-years 4
```

Runs offline against committed fixtures by default. Live data needs a key in `.env` (see `.env.example`); the fixture path is the default so nothing blocks on network access.

## Findings

**Day 1 - historical statement ingestion.** `data/GULFOILLUB/financials.csv` is reused verbatim from reverse-dcf-engine's own Day 2 transcription, per `NEXT_STEPS.md`'s own instruction to reuse project 2's company and cited sources rather than re-sourcing ten years of annual reports a second time (see `research/sources.md` for exactly what was and wasn't re-derived, and where the real page citations live). `model/historical.py` turns that flat, 14-column CSV into three typed objects per fiscal year (`IncomeStatement`, `BalanceSheetSummary`, `CashFlowSummary`) and checks two identities the source data implies by construction - `ebitda - depreciation_amortization == ebit` and `ebit - interest_expense - tax_expense == net_profit` - both pass cleanly on all 10 years, confirming the copy is byte-for-byte faithful to the source rather than corrupted in transit.

`python -m model.ingest --ticker GULFOILLUB` reports FY2014-15 through FY2023-24: EBIT margin ranges 11.68%-18.87%, net margin 7.75%-12.32%, and net debt swings from +₹6,333 lakh (FY2014-15, debt exceeds cash) to -₹37,293 lakh (FY2023-24, cash exceeds debt by a wide margin - a company that has been building a large net cash position, not drawing one down). Realized revenue CAGR over the 9-year span is **+14.54%**, matching reverse-dcf-engine's own figure for the same company and window exactly - a real cross-check that the copied data and the independently-written CAGR calculation here agree, not just a restated number.

**What this schema deliberately does not have, and why it matters for later days.** `BalanceSheetSummary` carries only `total_assets`, `total_debt`, `cash_and_equivalents` and `net_working_capital` - no `total_equity` field, because the source CSV has no liabilities/equity breakdown to derive one from honestly. `CashFlowSummary` carries only `capex` and the non-cash D&A add-back - no financing or working-capital-movement lines. Day 5's balance-check assertion (`assets = liabilities + equity`) cannot be built on this schema alone; it will need either a second transcription pass against the actual annual reports for the missing granularity, or an explicit, documented decision about what a plug here would mean (see `research/sources.md`). Flagged now rather than discovered as a Day 5 blocker.

20/20 tests pass (`tests/test_historical.py`): CSV structure/duplicate-year/non-numeric rejection, both identity checks against synthetic broken rows and the real fixture, the normalized dataclasses' derived properties (EBIT margin, net margin, net debt), and the CLI's success, missing-file, and identity-failure paths, all run against the real committed fixture as well as synthetic cases. `python -m model.ingest --ticker GULFOILLUB` and `--ticker NOPE` (the missing-data path) were both run by hand.

**Day 2 - driver-based revenue build.** Checked what Gulf Oil Lubricants India actually discloses before picking a driver, rather than assuming the "units x price" shape `NEXT_STEPS.md` suggests for a lubricants company. Searched all ten annual reports' text: no absolute sales volume (KL/litres/MT) is disclosed anywhere, only qualitative commentary ("volume growth 2-3x industry"), and the Ind AS 108 segment note states the Company has one reportable segment, "Lubricants" - there is no automotive/industrial or B2B/B2C revenue split in the audited statements either. A true units x price build cannot be done honestly here without inventing a volume base number, which this repo will not do - exactly the trap `NEXT_STEPS.md` names ("segment disclosure in Indian filings is often coarser than the driver build wants").

What every annual report *does* disclose, every year, is a mandatory geographic revenue split (India vs. Outside India). `model/revenue_driver.py` uses that as the real driver: `data/GULFOILLUB/segment_revenue.csv` sources `export_revenue` directly from each year's Note 37/38 (cited with PDF page numbers in `research/sources.md`), and domestic revenue is derived as `financials.csv`'s total revenue minus export revenue - not stored as a second number that could drift out of sync. Domestic and export revenue are then each modeled on their own historical CAGR (domestic +13.93%, export +34.21%, FY2014-15 to FY2023-24) and forecast forward independently, rather than one blended top-line growth percentage typed into a single cell. Export has grown from 1.47% of revenue in FY2014-15 to 6.14% by FY2023-24 - a real, structurally distinct trend this split actually captures that a single growth rate would average away.

26/26 new tests pass (`tests/test_revenue_driver.py`, 46/46 total): fiscal-year label arithmetic, CSV structure/duplicate rejection, the domestic+export-equals-total reconciliation against the real fixture (the core correctness check - every one of the 10 years sums exactly, and FY2016-17/FY2017-18's derived domestic figure independently reproduces the segment note's own reported "India" line to the rupee despite that note's total being gross of excise duty those two years), fiscal-year-mismatch and out-of-range sanity checks, segment CAGR and forecast math against hand-computed values, and the CLI's success, override, and three error paths (missing financials file, missing segment file, reconciliation failure), all run against the real committed fixtures. `python -m model.revenue --ticker GULFOILLUB` (default and with `--forecast-years`/growth overrides) and the `--ticker NOPE` missing-data path were both run by hand.

**Day 3 - cost structure, D&A, capex and working-capital schedules.** The data has no cost-by-nature breakdown (no cost of materials consumed, employee benefit expense, or other expenses line) and no PP&E gross block, so the cost structure uses the only honest aggregate available: EBITDA margin, not a bottom-up build - the same kind of disclosure gap Day 2 hit for segment volumes, handled the same way (pick the real driver the filings support, don't invent the one they don't). `model/schedules.py` expresses all four Day 3 schedules as margins of revenue, built straight off the already-ingested `HistoricalStatement`s. D&A is driven by revenue, not capex: checked by hand before picking the driver, D&A/capex swings 13%-394% across the ten historical years because D&A depreciates an accumulating gross block this data doesn't carry, while D&A/revenue drifts smoothly 0.50% -> 2.05% over the same span. Capex/revenue is genuinely lumpy (0.52%-8.10%, driven by discrete capacity expansions, e.g. FY2017-18's 8.10%) and NWC/revenue ranges 8.11%-23.66% with a level shift after FY2016-17 - both left lumpy rather than smoothed into a trend that isn't really there. Every margin defaults to a 3-year trailing average (overridable individually via `--ebitda-margin`/`--da-margin`/`--capex-margin`/`--nwc-margin`), picked over a single last year because capex especially is too noisy for one year to be a representative assumption. `model/costs.py`'s forecast chains directly onto Day 2's `forecast_revenue` output rather than re-deriving a revenue number, and also reports `delta_nwc`, the year-over-year change in working capital Day 5's cash-flow statement will need.

19/19 new tests pass (`tests/test_schedules.py`, 65/65 total): the historical schedule against hand-computed margins for the real fixture, the trailing-average helper's edge cases, forecast math against both default-margin and explicit-override cases, `delta_nwc` chaining across two forecast years, the Day 2 -> Day 3 revenue-forecast integration, and the CLI's success, zero-forecast, two missing-file, and override paths. `python -m model.costs --ticker GULFOILLUB` (default, with `--forecast-years 0`, and with all four margin overrides) and the `--ticker NOPE` missing-data path were all run by hand.

**Day 4 - debt schedule.** The source data has no split between term debt and a revolving facility, no disclosed amortization schedule, and no stated interest rate or revolver facility size - three separate gaps, each handled honestly rather than papered over with one invented number. `model/debt_schedule.py` treats historical `total_debt` as the opening term-debt balance and amortizes it at a flat, explicitly-labeled-as-an-assumption rate (`DEFAULT_AMORTIZATION_RATE = 10%`/year of the opening balance, overridable via `--amort-rate`); the revolver limit defaults to the historical peak `total_debt` (`default_revolver_limit`, overridable via `--revolver-limit`) since no facility size is disclosed either. The interest rate is the one piece that *is* derivable rather than invented: `interest_expense / average(total_debt)` gives a real implied effective rate for 9 of the 10 historical years (3.47%-10.93%, no clean trend), and the default interest rate is the trailing 3-year average of those implied rates (7.38%), the same override-the-driver pattern Day 3 used for margins.

The circularity this schedule has to resolve: interest on the *average* of opening and closing debt is standard (it does not overstate interest in a paydown year) but the closing balance depends on how much cash is left to pay the revolver down, which depends on interest expense, which depends on the closing balance. `--circular`/`--no-circular` makes the resolution a visible choice rather than an implementation detail: the default (`circular=True`) fixed-point-iterates interest against the average balance until it stops moving (bounded by `max_iterations`, and `converged=False` is reported rather than silently accepted if it doesn't); `--no-circular` charges interest on the opening balance only, a one-pass approximation that trades accuracy for not iterating. On the real fixture the two modes produce visibly different interest figures in every paydown year (e.g. FY2024-25: ₹2,309.75 circular vs. ₹2,431.31 non-circular) - a real, checkable difference, not a cosmetic flag.

Honest result on this company's real numbers: CFADS (the pre-tax, pre-interest proxy `EBITDA - capex - delta_nwc` the CLI derives from Day 3's own forecast) comfortably covers scheduled amortization and interest in every one of the 3 forecast years, so the revolver never draws and the `unmet_financing_gap` the schedule is built to report honestly if the facility limit is ever too small stays at zero throughout - the stress case is exercised only by the synthetic tests, not by this company's own fixture. That CFADS proxy is a deliberate, documented simplification: it excludes cash taxes, because cash tax depends on pretax income, which is EBIT minus *this schedule's own* interest output - taxing the proxy here would just relocate the circularity Day 5's full linkage has to resolve (income statement -> cash taxes -> debt schedule -> interest -> income statement) rather than resolve it, so it is left out and flagged rather than faked with an approximate tax figure.

27/27 new tests pass (`tests/test_debt_schedule.py`, 92/92 total): the historical implied-rate calculation against hand-computed values for the real fixture, the default interest-rate/revolver-limit derivations, amortization math (flat rate, floor at zero, default vs. override), the non-circular opening-balance interest calculation, the circular average-balance interest calculation (checked against its own definition: converged interest must equal rate times the average of opening and ending total debt) and that the two modes produce different numbers in a paydown year, revolver draw/repay/cash-sweep behavior under synthetic shortfall and surplus scenarios, the `unmet_financing_gap` path when a revolver limit is deliberately set too small to cover a shortfall, the real Day 3 -> Day 4 CFADS integration, and the CLI's success, zero-forecast-years, two missing-file, and override paths. `python -m model.debt --ticker GULFOILLUB` (default circular mode, `--no-circular`, and with all three parameter overrides) and the `--ticker NOPE` missing-data path were all run by hand.

**Day 5 - full linkage and the balance-check assertion.** The blocker flagged since Day 1 (`research/sources.md`, this README's own Day 1 Findings) was real: the source data has no liabilities/equity breakdown and no full cash-flow statement, so a literal `assets = liabilities + equity` check cannot be built by transcribing a real balance sheet split that does not exist in this data. Rather than invent one, `model/linkage.py` makes the same documented approximation `reverse-dcf-engine`'s own `capital_structure()` already made for this exact company: `equity_and_other_liabilities = total_assets - total_debt`, folding every non-debt liability (trade payables, provisions, deferred tax) into "equity" because no breakdown exists to split them honestly. The asset side gets the matching treatment: `other_assets = total_assets - cash - net_working_capital` (principally net fixed assets). Both are read directly off real historical columns for the base year, not solved for after the fact to force a match.

The forecast then rolls each side of the balance sheet forward **independently** — assets from a real cash-flow statement (net income + D&A - delta NWC - capex +/- debt movement, by the indirect method) plus a capex/D&A roll-forward of `other_assets`; liabilities+equity from Day 4's debt schedule plus retained earnings (net income, net of dividends) — and the balance check (`model.linkage.assert_balance_sheet_balances`) compares the two sides every year. When the plumbing is wired correctly the two sides are the same number by double-entry construction (worked through by hand in the module docstring): the identity is not independent proof the model is *right*, it is a trap for a *wiring* bug — a schedule's output silently not flowing into both sides — and `tests/test_linkage.py` proves the trap actually springs by constructing a deliberately broken year (one dropped number) and checking the assertion names it and raises, not just that the happy path passes.

Full linkage adds a second circularity on top of Day 4's own interest-vs-average-balance one: cash tax depends on pretax income, which is EBIT minus interest expense, which depends on the debt schedule, which now runs on CFADS *net* of cash tax (the exact circularity Day 4's own CFADS proxy flagged and punted on). Resolved with an outer fixed-point loop around Day 4's `forecast_debt_schedule`, called one forecast year at a time so each year's own tax/interest circularity converges before the next year's opening debt and revolver balances are fixed (`forecast_debt_schedule` gained an `initial_revolver` parameter for exactly this carry-forward, backward-compatible default `0.0`, since Day 4's own usage always resolved every year in one call and never needed to seed a nonzero opening revolver). Two more assumptions this data cannot supply, both named rather than hidden: there is no dividend line in `financials.csv` at all (not even an imperfect one), so the dividend payout ratio defaults to 0% (100% retained), overridable but not derived; and cash tax is floored at zero (no loss-carryforward or tax-credit mechanics modeled).

Honest result on the real fixture: all 3 forecast years balance to the cent (`balance_difference` is exactly `0.0000` printed to 4 decimal places) and both circularities converge every year. The circular-vs-non-circular interest figures for FY2024-25 (₹2,309.75 vs. ₹2,431.31) exactly match Day 4's own cited numbers for the same year — a genuine cross-check, not a coincidence: the revolver never draws on this fixture (same finding as Day 4), so CFADS's magnitude (now net of cash tax, unlike Day 4's pre-tax proxy) never actually influences the interest calculation, which depends only on the amortization schedule and the rate. That also means this fixture's real numbers never exercise the one part of the linkage Day 4 already flagged as synthetic-only (the revolver draw/repay path) — still true here, carried over as a Limitation rather than re-tested for real on data that doesn't stress it. 23 new tests pass (`tests/test_linkage.py`, plus 1 new test in `tests/test_debt_schedule.py` for `initial_revolver`; 115/115 total). `python -m model.statements --ticker GULFOILLUB` was run by hand in default (circular) mode, `--no-circular` mode, and with `--tax-rate`/`--dividend-payout` overrides (confirming a 30% payout both reduces retained equity and still balances, since the dividend is subtracted from cash and from equity identically).

**Day 6 - Excel export with live formulas.** `model/excel_export.py` writes a workbook with an **Assumptions** sheet (every rate, margin and limit the model needs - domestic/export growth, EBITDA/D&A/capex/NWC margins, amortization rate, revolver limit, interest rate, tax rate, dividend payout, balance tolerance - each a single yellow-filled cell) and a **Forecast** sheet where every cell past the "Base (last historical year)" column is a formula, never a pasted number: each forecast year references the previous column (for every roll-forward balance - term debt, revolver, cash, other assets, equity-and-other-liabilities) and the Assumptions sheet (for every rate/margin), the same reference-not-literal discipline this project's own `model.linkage` and `model.debt_schedule` already use in Python, now expressed as spreadsheet formulas instead of Python arithmetic. A **Historical** sheet carries the full 10-year ingested table for context/audit.

**Scope decision, made explicit rather than glossed over:** the workbook represents **non-circular** mode only (interest on the opening term-debt balance, matching `model.statements --no-circular`), not Day 4/5's circular average-balance mode. This was checked by hand to be more than a cosmetic simplification: with `circular=False`, `model.linkage.forecast_full_linkage`'s own outer tax/interest fixed-point loop converges on its first pass, because non-circular interest is a pure function of the opening balance and never depends on CFADS (which is downstream of tax, which is downstream of interest) - so *both* of Day 5's circularities disappear together, not just Day 4's, leaving a strictly left-to-right chain of formulas that needs no circular references or Excel's iterative-calculation setting at all. The circular mode stays a `model.statements --circular` (default) CLI-only feature; a reader who wants it does not get it in the workbook, and that gap is named here rather than hidden.

**Verified, not assumed.** Built the workbook with default assumptions (no overrides) for 3 forecast years, then recalculated it with LibreOffice headless (`soffice --headless --convert-to xlsx`, which forces a real formula recalculation rather than trusting openpyxl's uncomputed formula strings) and compared every recalculated number against `python -m model.statements --ticker GULFOILLUB --forecast-years 3 --no-circular`'s own printed output: revenue, EBIT, interest, tax, net income, total assets, total debt and equity-and-other-liabilities matched to the cent for all 3 years, and the balance check read `PASS` in every year. Repeated the same recalculation with `--tax-rate 0.25 --dividend-payout 0.2` and 5 forecast years - dividends flow from zero to a real non-zero figure and the balance check still passes every year, confirming the override wiring (Assumptions sheet -> Forecast formulas) actually works, not just the zero-override default path. 14 new tests pass (`tests/test_excel_export.py`, 129/129 total): every forecast-year cell past the Base column is asserted to be a formula string (never a literal), the Base column is asserted to hold only real historical facts or formulas built from them, Assumptions defaults are checked against the same CLI-printed numbers, override wiring is checked structurally, and the CLI's success, override, missing-file and zero-years paths are all run. `python -m model.build` was run by hand in default, 5-year, and tax-rate/dividend-payout-override modes (above), plus the `--ticker NOPE` missing-data path.

**What this does not cover, named as a limitation, not hidden:** the circular (average-balance) interest mode has no Excel representation - see the scope decision above. The Excel export also does not re-derive the revolver draw/repay path under a real stress scenario any differently than Day 4/5 already found: this fixture's CFADS still comfortably covers debt service in every forecast year, so the revolver formulas (`IF(cash_before_revolver>=0, ...)`) are exercised on the real fixture only on the repayment-of-zero branch, not the draw branch - correct by construction and recalculated by LibreOffice, but not stress-tested on real numbers, the same carried-over gap Day 4's own Limitations already named.

**Day 7 - sensitivity on the two assumptions that actually move the answer.** Rather than guess which two of this project's ten override flags (domestic/export growth, the four Day 3 margins, tax rate, interest rate, dividend payout, amortization rate) matter most - the kind of unchecked intuition ("growth and margin, obviously") this portfolio's own ground rules distrust - `model/sensitivity.py` measures it: each lever is shocked up and down from its own real default (the same trailing-average/CAGR/implied-rate resolution `model.linkage.forecast_full_linkage` already performs for an omitted override, now exposed via six new override parameters that function gained for this day, threaded straight through to Day 2's `forecast_revenue` and Day 3's `forecast_schedule`), one at a time with every other lever held at default, and ranked by the resulting swing in FY-final (FY2026-27, 3y forecast) net debt/EBITDA. That output, not `fy3_revenue_cagr` or `fy3_ebit_margin`, is the ranking target on purpose: a growth override *is* the revenue CAGR and an EBITDA-margin override *is* the EBIT margin (net of a roughly stable D&A margin) by construction, so ranking against either would only prove that overriding a number changes that same number - net debt/EBITDA is a genuinely downstream result of all ten levers combined.

Honest result on the real fixture: **dividend payout** ranks #1 (impact 0.34x) and **domestic revenue growth** ranks #2 (0.21x), ahead of capex margin, NWC margin, tax rate, D&A margin, EBITDA margin, export growth, interest rate and amortization rate (0.18x down to 0.01x) in that order. Dividend payout ranking first is not a coincidence of a well-chosen shock: Day 5's own Limitations already flagged that no dividend data exists in this data at all, so the model retains 100% of earnings by default - how much of that retained cash actually gets swept to debt paydown versus paid out is mechanically the single biggest lever on leverage in this build, and the finding simply confirms that structural fact numerically rather than asserting it. Domestic growth outranking export growth (0.21x vs. 0.02x) reflects export's still-small base (6.14% of FY2023-24 revenue per Day 2) - a given percentage-point shock to the much larger domestic segment moves more absolute cash through the model. The 2-D grid (`--steps 2`, five values each side of default) tabulates net debt/EBITDA across dividend payout x domestic growth; every one of its 25 combinations was checked to still pass the Day 5 balance-check assertion (`tests/test_sensitivity.py::test_sensitivity_grid_every_cell_still_balances`), confirming the sensitivity sweep never silently drifts into a wiring-broken scenario.

**A real asymmetry, named rather than smoothed over:** dividend payout's default is 0.0 and this project only floors ratios at zero (a negative payout, margin, tax or amortization rate is not a real scenario here; growth is the one lever allowed to go negative, since a segment can genuinely shrink). That means dividend payout's "down" shock is a no-op (0.0 - 0.20 floors back to 0.0, identical to the base case), so its ranking is really a one-sided measurement - the up-shock alone - while every other lever's ranking is the larger of two real, distinct shocks. The grid's own row values collapse the same way (`sensitivity_grid`'s `_dedupe` drops the repeated 0.0% rows a naive five-step grid would otherwise print three times over), which is itself evidence of the asymmetry rather than a glossed-over quirk. **The shock sizes themselves are also a judgment call, not derived:** each lever's +-/- step (20pp for payout, 5pp for growth/tax/amortization, 2pp for EBITDA/NWC/interest, 1pp for D&A/capex) was picked to roughly span that lever's own plausible range rather than, say, one historical standard deviation - a different, defensible shock-sizing convention could rank the ten levers differently, and that sensitivity-to-shock-size is not itself tested here.

12 new tests pass (`tests/test_sensitivity.py`, 150/150 total): the two new `forecast_full_linkage` override parameters against both the omitted-vs-explicit-`None` equivalence and a real growth/margin bump; `net_debt_to_ebitda`'s hand-computed value and its `None` path for non-positive EBITDA; the zero-floor on every ratio lever except growth and the no-floor allowance for growth going negative; `resolve_base_assumptions` against Day 2's and Day 4's own README-cited figures (domestic +13.93%, export +34.21%, interest rate 7.38%); the ranking's coverage of all ten levers and its sort order; the dividend-payout floor's no-op down-shock specifically; the grid's shape for two unfloored levers, its dedup for a floored one, one cell checked directly against calling `forecast_full_linkage` itself (never re-deriving the comparison independently), and the full-grid balance-check sweep above; and the CLI's success, two missing-file, zero-forecast-years and non-positive-steps paths. `python -m model.sensitivity --ticker GULFOILLUB` was run by hand in default (circular), `--no-circular`, `--steps 1`, and the `--ticker NOPE` missing-data path.

**Day 8 - the worked "what happens if they draw the revolver in year two" scenario.** Day 4/5's own Limitations already named the gap this day has to answer honestly: on Gulf Oil Lubricants India's real numbers, CFADS covers debt service in every forecast year, so the revolver never actually draws - the standard interview probe ("what happens to your model if they draw the revolver in year two") has no real answer to point to without forcing one. `model/revolver_scenario.py` forces exactly one: every forecast year runs at the same real historical defaults `model.statements` already uses, except a chosen year (default: year 2), which gets a deliberately collapsed EBITDA margin (5%, versus the real ~14.3% baseline) - a demand or cost shock, isolated to one year, not a change to every assumption at once.

Doing that without changing `forecast_full_linkage`'s signature (every one of its ten overrides already applies uniformly to every forecast year, by design, for Day 7's sensitivity sweep) meant calling Day 2/3's own revenue and schedule forecasters twice - once for the years before the shock at baseline assumptions, once for the shocked year(s) - and stitching the two `ForecastScheduleYear` lists together before handing them to the same tax/interest circularity loop `forecast_full_linkage` already runs. That loop was pulled out into a new `model.linkage.forecast_linkage_from_cost_forecasts` so it is reused, not reimplemented; `forecast_full_linkage` itself is now four lines that build one cost forecast and call it, checked to still produce byte-identical output against the real fixture (`tests/test_linkage.py::test_forecast_linkage_from_cost_forecasts_matches_forecast_full_linkage`).

The worked numbers, `python -m model.revolver --ticker GULFOILLUB` (4y forecast, circular mode, shock year 2, shock margin 5%): FY2024-25 is unshocked and healthy (₹54,011 lakh EBITDA, no draw, cash ₹81,896 lakh). FY2025-26 is the shock - EBITDA collapses to ₹21,821 lakh, CFADS after tax can no longer cover scheduled amortization (₹2,964 lakh) plus interest (₹2,117 lakh), and the revolver draws ₹1,042 lakh against a ₹35,700 lakh limit (97% headroom still unused - this shock is nowhere near breaching the facility). Cash holds exactly flat at ₹81,896 lakh that year: the draw is sized to plug precisely the gap operations opened up, not a cosmetic number. FY2026-27, with the margin back to baseline, EBITDA recovers to ₹72,050 lakh and the cash sweep repays the entire ₹1,042 lakh draw in one year, before any scheduled amortization on the term debt is affected. FY2027-28 lands on ending total debt of ₹21,606 lakh - **identical to the never-shocked path** (`tests/test_revolver_scenario.py::test_the_scenario_recovers_to_the_unshocked_path_once_the_revolver_is_cleared`) - because the revolver, not the term debt's own amortization schedule, absorbed the whole shock and was fully cleared before it could touch anything else. A persistent shock (`--shock-duration 3`, margin never recovers) behaves differently and is shown too: draws of ₹1,042 lakh and ₹244 lakh in years 2-3, tapering rather than compounding, because revenue keeps growing at its real historical CAGR even though the *margin* stays depressed - absolute EBITDA eventually outgrows the fixed-margin shock, and year 4 nets a ₹570 lakh repayment with no further draw.

**What this honestly does and does not show.** This is a demand/margin shock, not a cash-flow-timing shock - growth, D&A, capex and NWC margins are untouched, so the mechanism is "EBITDA falls, debt service doesn't," not "a working-capital swing or a one-off capex spike needs bridging," which is a different, equally real reason a revolver draws that this scenario does not model. The shock size (5% margin, chosen to draw a meaningfully sized but not facility-breaking amount against the real fixture) is a judgment call for illustration, the same kind Day 7's shock sizes already were - a smaller shock might not draw at all, a much larger one would hit the revolver limit and report `unmet_financing_gap`, a path this scenario's real fixture never reaches (see `model.debt_schedule`'s own synthetic tests for that path). 13 new tests pass (`tests/test_revolver_scenario.py`, plus 3 for the `forecast_linkage_from_cost_forecasts` extraction in `tests/test_linkage.py`; 172/172 total). `python -m model.revolver --ticker GULFOILLUB` was run by hand in default (circular, one-year shock), `--no-circular`, `--shock-duration 3` (persistent), `--shock-year 1` (no pre-shock baseline to resolve from), and two error paths (`--ticker NOPE`, a shock span that overruns `--forecast-years`).

## Limitations and what would make me wrong

- A forecast is a set of assumptions, not a prediction. `model/sensitivity.py`'s ranking shows dividend payout and domestic revenue growth actually move FY-final net debt/EBITDA the most on this fixture (0.34x and 0.21x respectively, versus 0.01x-0.18x for the other eight levers) - but the ranking itself depends on the shock sizes chosen for each lever (see the Day 7 Findings above), which are a judgment call, not derived, and dividend payout's #1 rank is inflated by being the only lever with a one-sided (floored-at-zero) down-shock rather than two real ones.
- Segment disclosure in Indian filings is often coarser than the driver build wants, so some drivers are estimated and flagged. Concretely for Gulf Oil Lubricants India: no annual report discloses an absolute sales volume figure (KL/litres/MT), only qualitative volume-growth commentary, and the Ind AS 108 segment note reports a single "Lubricants" segment with no automotive/industrial or B2B/B2C revenue split. `model/revenue_driver.py`'s domestic-vs-export driver is the real substitute - the one quantitative, decomposable split the filings actually give every year - not a units x price build.
- The domestic/export split's historical CAGRs (`model.revenue_driver.segment_cagr`) are extrapolations of a 9-year trend, most pronounced for export (+34.21% CAGR off a small base, now ~6% of revenue). Naively compounding that rate for many years would make exports an implausibly large share of revenue; `model/revenue.py --export-growth` exists precisely so a later day's full build can override it with a decelerating or capped assumption instead of trusting the historical CAGR forever.
- Share count is held flat at its last historical value for the whole forecast; no corporate action (bonus issue, split, buyback, rights issue) is modeled anywhere in this repo, so a real one during the forecast window would change the actual share count and this model would not reflect it.
- `data/GULFOILLUB/financials.csv` is reused from reverse-dcf-engine's own transcription (see `research/sources.md`), not independently re-sourced. It carries no balance-sheet liabilities/equity breakdown and no full cash-flow statement - `model.historical.BalanceSheetSummary` and `CashFlowSummary` only expose the fields the source data actually has (`total_assets`/`total_debt`/`cash_and_equivalents`/`net_working_capital`, and `capex`/D&A respectively). Day 5 resolved this with a documented approximation rather than a second transcription pass: `model.linkage` folds every non-debt liability into "equity" (`equity_and_other_liabilities = total_assets - total_debt`), the same simplification reverse-dcf-engine's own `capital_structure()` already made for this company. This understates real liabilities and overstates "equity" - a real bias, same direction and same root cause as reverse-dcf-engine's own capital-structure caveat, not a new one invented here.
- `model/linkage.py`'s balance check is an algebraic identity once the three statements are correctly wired (worked through by hand in that module's docstring), not independent third-party verification that the model's output is correct. It is a trap for a wiring bug - a schedule's output silently not reaching both the asset and the liability side - proven to actually spring in `tests/test_linkage.py` via a deliberately broken synthetic year, not just a happy-path pass.
- No dividend line exists anywhere in `financials.csv`, so the dividend payout ratio (`model.linkage`'s `--dividend-payout`, default 0%) is an assumption, not even an imperfectly derived number - unlike every other rate/margin in this project (interest, tax, EBITDA/D&A/capex/NWC margins), which are at least real historical ratios. A real dividend-paying company's book equity would grow more slowly than this model's default (100% retention) projects.
- Cash tax is floored at zero in `model.linkage` - no loss-carryforward or tax-credit mechanics are modeled. Not a live issue on this fixture (pretax income is positive in every historical and forecast year), but it would understate a loss year's cash position if ever applied to a company that has one.
- The revolver draw/repay/cash-sweep path, flagged as synthetic-only in Day 4's own Limitations, is still synthetic-only *on this company's real, unshocked numbers* after Day 8: CFADS comfortably covers debt service every real forecast year even after now being computed net of cash tax, so the real fixture never draws organically. Day 8's `model.revolver_scenario` exercises the real mechanism end to end on this fixture by forcing a deliberate margin shock rather than inventing a synthetic company - a genuine improvement over "only unit tests touch this code path" - but the shock, its size, and which year it lands in are all choices made for the worked example, not something Gulf Oil Lubricants India's own filings or forecast ever produce unprompted. `initial_revolver`, the parameter `model.debt_schedule.forecast_debt_schedule` gained so Day 5 could carry a revolver balance across its own year-by-year calls, is exercised by both the synthetic test (`test_forecast_debt_schedule_accepts_a_nonzero_initial_revolver`) and, now, Day 8's shocked scenario.
- Day 8's revolver-draw scenario shocks EBITDA margin only; growth, D&A, capex and NWC margins stay at their real historical defaults for every year, including the shocked one. A working-capital crunch or a one-off capex spike are at least as realistic a reason a revolver draws as a margin collapse, and this scenario does not model either - it answers "what happens if the revolver draws," not "every way the revolver could end up drawing."
- The two Day 1 identity checks (`ebitda - D&A == ebit`, `ebit - interest - tax == net_profit`) are tautologies by construction, since reverse-dcf-engine derived those columns that way from two reported numbers in the first place. Passing them confirms the copy wasn't corrupted; it is not independent evidence the ten years of hand-transcribed figures are correct against the original filings - that assurance is only as strong as reverse-dcf-engine's own citation ledger.
- `model/schedules.py`'s cost structure is EBITDA margin only - there is no cost-of-materials/employee-cost/other-expense breakdown in the source data to build a bottom-up cost structure from. D&A is modeled as a margin of revenue rather than of capex specifically because D&A/capex is not stable here (13%-394% across the ten historical years) without a PP&E gross block this data doesn't carry. Capex/revenue (0.52%-8.10%) and NWC/revenue (8.11%-23.66%, with a level shift after FY2016-17) are both genuinely lumpy, not smoothly trending; the default 3-year trailing average is a deliberate smoothing choice, not a claim that the lumpiness is noise - a future capacity expansion like FY2017-18's would push realized capex well above what `model/costs.py`'s trailing average projects.
- `model/debt_schedule.py` has to invent two things the filings never disclose: the source data gives one blended `total_debt` figure, not a term-debt/revolver split, an amortization schedule, or a revolver facility size. The 10%/year flat amortization rate and the historical-peak-`total_debt` revolver limit are both labeled assumptions, individually overridable, not facts read off a loan agreement - treat the resulting ending-debt path as illustrative, not as this company's actual repayment schedule. The interest rate is the one derived figure (`interest_expense / average(total_debt)`, trailing-averaged), which is real but still only an aggregate effective rate across whatever mix of facilities this company actually has, not a single bond's coupon.
- `model/excel_export.py`'s workbook represents **non-circular** mode only - interest on the opening term-debt balance, matching `model.statements --no-circular` - never Day 4/5's circular average-balance mode. This removes the circularity Excel would otherwise need its iterative-calculation setting for, but a reader who specifically wants the circular mode's numbers has to use the CLI, not the workbook; the gap is named in the module's own docstring and in the Day 6 Findings above, not hidden.
- The revolver, cash-sweep, and `unmet_financing_gap` logic is exercised end to end only by `tests/test_debt_schedule.py`'s synthetic cases - on Gulf Oil Lubricants India's own real cash flow, CFADS (the Day 3-derived, pre-tax, pre-interest proxy `model/debt.py` computes) comfortably covers debt service in every forecast year, so the revolver never actually draws against the real fixture. The draw/repay/shortfall paths are correct by construction and by test, not yet by a real stressed example.
- The CFADS proxy `model/debt.py` feeds the debt schedule (`EBITDA - capex - delta_nwc`) deliberately excludes cash taxes. Taxing it properly needs pretax income, which is EBIT minus this same schedule's own interest output - computing it here would relocate, not resolve, the circularity Day 5's full linkage has to close (income statement -> cash taxes -> debt schedule -> interest expense -> income statement). Interest and debt balances in this day's output are therefore modestly overstated relative to what a tax-aware CFADS would produce, by the amount of the (unmodeled) interest tax shield on cash available for repayment.

These are the real numbers off the GULFOILLUB fixture's default 3-year forecast, not illustrative placeholders. `net_debt_ebitda_fy3` is negative because this company's modeled FY3 cash balance exceeds total debt — a net cash, not net debt, position, which is itself worth naming rather than smoothing over: the ratio is doing its job (nothing to lever against), not misbehaving.

On the spine side, `stockstalker.gates.fundamentals` reads this file and attaches it to the one screen candidate whose ticker matches, the same non-match-by-default pattern as v0.7's reverse-dcf-engine integration — GULFOILLUB is not in Stock Stalker's 3-ticker fixture universe (RELIANCE/TATACHEM/CROMPTON), so the gate logic is proven against a synthetic contract keyed to a universe ticker; see that repo's own README for the real-data non-match.

Communication is by file contract, not imports, so either side can be refactored without breaking the other.
